How the content pipeline works

From a new project, to a full set of reviewed and exported content — step by step

Plain-language walkthrough of the system architecture, and who or what is responsible for each part

1

A new project is created

An operator opens the dashboard and starts a project, entering the client's starting details — name, industry, region, and any known background. This becomes the project's first stored context.

2

The system checks who is asking

Every request carries the operator's role. Operators can only run stages on projects assigned to them; only admins can edit prompt templates or manage staff. This is checked before any stage is triggered.

3

The Workflow Engine checks dependencies

Before a stage can run, the Workflow Engine confirms every stage it depends on is already approved. If not, the request is rejected with a clear reason rather than run against incomplete context.

4

Existing context is pulled in

Anything already approved for this project — persona details, prior analysis, design decisions — is loaded from the Context Store, so each stage builds on real, structured facts instead of repeating earlier work.

5

The stage is queued for background execution

The task is placed on the Redis queue and picked up by a Celery worker, so the operator's screen is never blocked while a stage runs.

6

The prompt template is rendered with context

The worker fetches the correct versioned prompt template for this stage and fills it in with the project's current context fields, following the exact instructions and guardrails written into that template.

7

Claude generates the content

The rendered prompt is sent to the Anthropic Claude API. The result comes back as structured content specific to that stage — a persona, an analysis, a page design, a piece of written content.

Stage type decides what happens next
Gated stages pause here

Persona, Analysis, and Design are saved as awaiting_review and wait for a human before anything downstream can start.

Auto-chain stages continue

Everything after Design is saved as approved immediately and the next stage in sequence is queued right away.

8

An operator reviews a gated stage

The operator reads the draft, edits it directly if needed, and approves or rejects it. Approving writes the final content into the Context Store as new, reusable facts for later stages. Rejecting sends the stage back to be re-run.

✓ Approved → context saved, next stage unlocked ✗ Rejected → stage reset, can be re-run
9

The finished content is stored and ready to export

Approved content is written to the database and saved to the backend's Railway volume. The operator can export it as Markdown or HTML at any time, and the project dashboard shows the full status of every stage, start to finish.

A few things that apply the whole way through

Not single steps — these run across everything above

Data stays isolated per project

Every database query is filtered by project_id. One project's data is never visible to another.

A person always has the final say on gated stages

Persona, Analysis, and Design cannot move forward without an explicit operator approval.

Failures only affect the failed stage

If a Claude call fails, only that stage is marked failed and retried. Prior approved context and output are never lost.

Templates are versioned

A stage always uses the template version that was active when its project reached that point, so editing a template never disrupts work already in progress.

Nothing is lost

Every run, approval, rejection, and export is recorded against the project, giving a full, traceable history of what happened and when.
