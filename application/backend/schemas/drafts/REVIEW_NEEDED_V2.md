# Field Schema Registry — Draft Review Needed (v2)

Generated by hand during the `application/backend/assets/Prompts/` migration (superseding the
`manual_execution/`-sourced registry). Every file in this directory was read in full against the new
canonical prompt set. The items below are the ones that could not be resolved by reading the source
text alone and need a human decision, per the same bar applied in the original `REVIEW_NEEDED.md` pass.

---

## 1. `required_if` taxonomy can't express an OR condition — `cro.json` / `parent_pillar_page_url`

Source (`Master_Prompt_Universal_Page_Rewrite_v1.md`): *"Parent Pillar Page URL (required if scope =
SUB-SERVICE or LOCATION): `[YOUR ANSWER / N/A]`"*.

The `required_if` extension introduced in the first review pass (`{"field": "x", "equals": "y"}`) only
expresses a single-value equality. This field is required when `page_scope` equals **either**
`SUB-SERVICE` **or** `LOCATION` — a two-value OR condition the current taxonomy has no key for. I left
it `required: false` with the condition spelled out in `fallback_instruction` rather than inventing a
new taxonomy extension (e.g. `required_if_any` / `equals: [...]`) unilaterally. **Decision needed:**
extend `required_if` to accept a list (`"equals": ["SUB-SERVICE", "LOCATION"]`) or add a distinct key —
whoever builds the Validation Gate (Day 4-6) should pick one and apply it consistently, since this
OR-condition shape will likely recur (e.g. other master prompts using the same PILLAR/SUB-SERVICE/
LOCATION/PRODUCT-CATEGORY/COMPARISON taxonomy).

## 2. `cro_framework` field doesn't fit any existing `kind` cleanly — `cro.json`

Source: *"CRO Framework: `[PASTE OR ATTACH — or write "USE DEFAULT" to use the framework embedded in
Step 1A below]"*. This isn't a normal optional-with-fallback field (the fallback isn't a context-store
value or a computed default — it's literal instruction text embedded in the prompt itself,
reproducing `CRO_Framework_Universal_v1.md`). I modeled it as `kind: "text"` with
`"default": "USE DEFAULT"`, but this doesn't cleanly distinguish "the user pasted framework text" from
"the user explicitly asked to fall back to the embedded default" for audit/reproducibility purposes.
**Decision needed:** confirm whether `kind: "text"` + `default` is sufficient, or whether this pattern
(attach-a-document-or-invoke-an-embedded-default) deserves its own `kind` (e.g. `reference_document`)
in the taxonomy, since the same "USE DEFAULT" pattern could recur for other framework/reference docs.

## 3. Locked-content fields in `cro.json` — required vs. optional is inconsistent in the source itself

Source lines: `Locked Offer / Service / Product Names: [LIST VERBATIM]`, `Locked Section Names or
Headings: [LIST VERBATIM]`, and `Locked Content Blocks: [PASTE VERBATIM]` give no "/NONE" or "/N/A"
alternative (unlike `Locked Legal / Compliance Text: [PASTE VERBATIM / NONE]`, which explicitly does).
Taken literally, the first three could be read as required-if-anything-is-locked-but-otherwise-blank,
which the source doesn't actually resolve. I modeled all four as `required: false` with a
`fallback_instruction` ("leave blank or write NONE if nothing is locked yet for this client") for
consistency, but this is an inference, not a literal reading. **Decision needed:** confirm optionality
for `locked_offer_service_product_names`, `locked_section_names_or_headings`, and
`locked_content_blocks` in `cro.json`.

## 4. Pillar Page / SEO Pillar Page terminology-map fields — text re-entry vs. auto-pulled context

`pillar_page.json` and `seo_pillar_page.json` both carry three terminology-map fields (`word_for_the_reader`,
`word_for_the_thing_being_chosen_between`, `word_for_the_first_commitment_step`) that the source text says
must "match the copy prompt's resolution — keeps design and content consistent" (i.e., reuse whatever the
CRO stage already resolved for this client). I modeled these as `kind: "text"`, `source: "user_input"`,
`required: true`, with a `fallback_instruction` pointing back to the CRO stage's resolution — matching how
the prompt file itself presents them (as fillable rows, not as an attached document). An alternative
reading: these should be `kind: "context_reference"` fields auto-resolved from a `cro_terminology_map`
context-store entry (which doesn't currently exist as a named write-key anywhere in
`Marketing_in_a_Box_Session_Context.md` §6 — the CRO stage's declared writes are only
`cro_audit_findings`, `cro_rewritten_copy`, `cro_locked_sections`). **Decision needed:** either (a) add a
`cro_terminology_map` write-key to the CRO stage's outputs and convert these three fields to
`context_reference` in both Pillar Page schemas, or (b) confirm the current text-field-with-fallback-
instruction modeling is acceptable for Day-1 purposes. The same three fields also appear as required
text inputs on the `cro.json` schema itself (where they originate) and on `Master_Prompt_Universal_Value_Ladder_v2.md`'s
optional "Terminology map" section (`offers_v2.json`) — worth resolving once, consistently, across all
three schemas rather than per-file.

## 5. `book.json` — two context_reference fields not evidenced in the new prompt's own text

`content_marketing_strategy_optional` and `plan_of_action_summary_optional` were added to `book.json`
solely because `Marketing_in_a_Box_Session_Context.md` §6 lists Book as reading
`content_marketing_strategy` and `plan_of_action_summary`. A full read of
`Webinar-to-Book-Architect-Prompt.md` found no explicit mention of a Plan of Action reference anywhere
in the file (`content_marketing_strategy` has only an indirect one, via Step 6's "one asset feeds many
derivative assets" line). **Decision needed:** confirm whether the old §6 wiring for Book is still
accurate against this new prompt, or whether `plan_of_action_summary_optional` should be dropped as a
stale carry-over from the pre-migration DAG design.

## 6. `podcast.json` — `webinar_script_optional` not evidenced in the new prompt's own text

Same pattern as #5: `Marketing_in_a_Box_Session_Context.md` §6 lists Podcast as reading `icp_*,
webinar_script, plus a supplied podcast transcript source`, but a full read of
`universal-podcast-prompt.md` found no reference to a webinar script/transcript anywhere in the file —
only "Competitor Podcast Sources" (podcast-specific, not webinar) and generic "approved copy... earlier
in this conversation." **Decision needed:** confirm whether Podcast genuinely should auto-pull the
Webinar stage's script, or whether this was specific to the old asset order and no longer applies now
that Webinar and Podcast both independently pull from competitor sources of their own medium.

## 7. Competitor Analysis `excluded_competitors` field — source of the dedup list is unclear

All 10 `competitor_analysis_*.json` schemas model `excluded_competitors` as `source: "user_input"`
(a manually-supplied list of domains to exclude on a re-run), matching the literal source text
(`excluded_competitors: [list any domains already sourced in prior runs]`). An equally plausible
reading: this should be `source: "auto_from_context"`, auto-populated by the system from that same
stage's own prior output(s) for this client, rather than something the user re-types by hand.
**Decision needed:** confirm whether re-running a competitor-analysis stage should auto-carry-forward
its own prior domain list (system-managed dedup) or remain a manual field (current modeling).

## 8. Funnel's "browse the live site" and generic "competitor analysis" dependencies

`funnel.json` models two fields — `competitor_analysis` and `client_website_url_live_reference` — with
`context_key: "unresolved_context_key"`, following the convention from the original `offers_v1.json`
review resolution for genuinely un-mappable references. Funnel has no paired numbered competitor file
(confirmed — no `0X_` filename appears anywhere in `Funnel_Prompt.md`), and "browse the client's website
established earlier in this conversation" isn't a context-store read in the classic sense (it's a live
fetch, not a stored field). **Decision needed:** whoever builds the Context Resolver should decide
whether "browse the live site" deps like this one need their own `source` value (distinct from both
`user_input` and `auto_from_context`) rather than being folded into the existing two-value taxonomy.

## Resolution log (2026-08-13)

1. **`required_if` OR-condition (item 1)**: resolved. `required_if.equals` now accepts a list —
   `cro.json`'s `parent_pillar_page_url` uses `{"field": "page_scope", "equals": ["SUB-SERVICE", "LOCATION"]}`.
   Whoever builds the Validation Gate should treat `equals` as "matches any value in the list" when it's
   an array, "matches exactly" when it's a scalar (backward-compatible with every existing `required_if`/
   `conditional_on` use).

2. **`cro_framework` kind (item 2)**: kept as `kind: "text"` + `default: "USE DEFAULT"` for Day-1 purposes,
   per user confirmation. Not revisited.

3. **Locked-content fields optionality (item 3)**: the inferred `required: false` + "leave blank or write
   NONE" modeling confirmed as acceptable. Not changed.

4. **Terminology map: context_reference vs. re-entry (item 4)**: resolved. `cro.json` now declares
   `writes_context_keys` including a new `cro_terminology_map` key (composed from its own
   `word_for_the_reader` / `word_for_the_thing_being_chosen_between` / `word_for_the_first_commitment_step`
   fields, which stay as `user_input` there — that's where they're first resolved). `pillar_page.json`,
   `seo_pillar_page.json`, and `offers_v2.json`'s equivalent fields are now `context_reference` fields
   pulling from `cro_terminology_map` via a new `sub_key` attribute, falling back to `ask_user_if_missing`
   if CRO hasn't run yet.

5. **`book.json` stale wiring — `plan_of_action_summary_optional` (item 5)**: kept as-is (optional,
   `fallback: ask_user_if_missing`). Reasoning: it's a soft/optional read that costs nothing when absent
   and preserves a potentially useful cross-asset connection — consistent with how item 6 was resolved.
   Not treated as a blocking ambiguity.

6. **`podcast.json` stale wiring — `webinar_script` (item 6)**: same reasoning as item 5 — kept as an
   optional context_reference, not removed.

7. **Competitor Analysis `excluded_competitors` sourcing (item 7)**: resolved in favor of system-managed
   dedup. All 10 `competitor_analysis_*.json` schemas now set `excluded_competitors` to
   `source: "auto_from_context"`, `context_key: "<own asset_id>"` (self-referential — this stage's own
   prior output for this client), `fallback: "treat_as_empty_if_missing"` (new fallback value: on a first
   run, treat as an empty list rather than prompting the user).

8. **Funnel's live-fetch dependency (item 8)**: resolved. `funnel.json`'s `client_website_url_live_reference`
   field now uses a new `source: "live_fetch"` taxonomy value (distinct from `user_input`/`auto_from_context`),
   with `fallback: "skip_silently_if_missing"`. The generic `competitor_analysis` field (no paired numbered
   competitor file for Funnel) was left as `auto_from_context` / `unresolved_context_key` — that one wasn't
   actually a taxonomy problem, just a stage with no dedicated competitor source.

9. **`competitor_analysis_book` DAG gap** (surfaced by the DAG-seeding agent, not originally in this file):
   resolved. Added as row 23 in `scripts/seed_asset_definitions.py` (sonnet tier, no deps). `book`'s
   `depends_on` stays `[webinar, icp]` unchanged — `competitor_analysis_book` is wired as an optional
   schema-level read only (`book.json`'s `competitor_book_positioning` field, already present from the
   schema-rebuild pass), not a hard DAG edge, since the source prompt's own text never references it.

*New taxonomy values introduced this pass: `required_if.equals` as a list; `source: "live_fetch"`;
`fallback: "treat_as_empty_if_missing"` / `"skip_silently_if_missing"`; `sub_key` on context_reference
fields. All documented here and in the affected schemas' inline comments — no separate spec file yet.*
